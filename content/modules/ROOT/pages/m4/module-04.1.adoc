== 개념 소개 및 모듈 개요

include::../style.adoc[]

기존 애플리케이션을 가져오기 위해 소프트웨어 템플릿을 사용하는 것과 관련된 몇 가지 개념을 살펴보겠습니다.

=== 카탈로그 정보: A Refresher

여러분은 이미 `catalog-info.yaml` 파일의 마법을 보았습니다. {product_name_rhdh}는 리포지토리 내에 `catalog-info.yaml` 파일이 있는지에 따라 컴포넌트트를 식별하고 가져올 수 있습니다. 이 파일에는 다음과 같은 내용이 포함됩니다.

* 유용한 링크
* 소유권 정보
* TechDocs를 찾는 방법에 대한 지침
* 컴포넌트와 다른 엔터티 간의 관계

적절한 플러그인과 구성을 사용하여 ``catalog-info.yaml``에 구성 정보를 추가하면 {product_name_rhdh}의 컴포넌트 보기에서 중요한 정보를 표시할 수 있습니다.

* CI 파이프라인
* CD 배포
* Git 병합 상태
* 클러스터 세부 사항
* API 문서

=== Inner-Loop와 Outer-Loop란 무엇인가

애플리케이션 개발 및 배포 주기는 **내부 루프(Inner-Loop)**와 **외부 루프(Outer-Loop)**로 정의할 수 있습니다.

image:m4/inner-outer-loops.png[width=60%] 

* **내부 루프(Inner Loop)**는 개발자가 코드를 작성하고, 테스트하고, 디버깅하는 반복적인 개발 주기로, 코드가 공유 환경에 통합되기 전에 로컬에서 진행됩니다. 개발자는 주로 내부 루프 내에서 작업을 하며, 많은 조직에서는 내부 루프가 일반적으로 개발자의 컴퓨터에서 이루어집니다. 그러나 이 워크샵에서는 내부 루프를 OpenShift의 임시 환경(네임스페이스) 내에서 정의합니다.
+
NOTE: 임시 환경은 특정 기능을 구축하는 데 사용되는 일회성 환경으로, 기능 개발이 완료되면 폐기될 수 있습니다.

* **외부 루프(Outer Loop)**는 개발자가 코드를 버전 관리 시스템에 푸시할 때 시작됩니다. 이 루프는 통합, 검증, 컴플라이언스 및 보안 점검, 그리고 목표 환경으로의 배포 등을 포함합니다. 일반적으로 이 과정은 플랫폼 엔지니어들이 작업하는 영역입니다.

두 루프는 독립적으로 운영되지만, 개발자가 Git에 코드를 푸시하면 외부 루프가 트리거됩니다.

=== 의견이 있는 접근 방식(An Opinionated Approach)

NOTE: 각 조직은 내부 루프와 외부 루프를 달성하는 방법에 있어 서로 다를 수 있습니다. 이 모듈은 내부 루프와 외부 루프에 대한 매우 의견이 강한 접근 방식을 제시합니다. 주요 목적은 {product_name_rhdh}와 함께 가능한 방법을 보여주는 것입니다.

기존 애플리케이션을 {product_name_rhdh}에 대규모로 가져오는 것을 확장 가능하게 만들기 위해, 플랫폼 엔지니어링(PE) 팀은 **소프트웨어 템플릿(Software Template)**을 만들어 `catalog-info.yaml` 파일과 TechDocs 스켈레톤 구조의 생성을 자동화합니다.

이 기존 애플리케이션에 필요한 카탈로그 정보와 TechDocs는 두 가지 위치 중 하나에 저장될 수 있습니다.

. 새 파일을 기존 소스코드와 동일한 Git 리포지토리에 추가할 수 있습니다.
. 또는 ``kind: Location``인 엔티티가 포함된 별도의 리포지토리를 생성하여 모든 ``catalog-info.yaml``과 TechDocs 파일을 저장할 수 있습니다. ``kind: Location`` 엔티티는 다른 카탈로그 데이터를 찾아볼 위치를 참조합니다.

*Parasol team's approach*

Parasol 팀은 기존 소스코드를 수정하지 않기 위해 두 번째 접근 방식을 선택합니다.

* 그들은 ``all-location-parasol``이라는 Location 전용 리포지토리를 만들고, 여기에 https://backstage.io/docs/features/software-catalog/descriptor-format/#kind-location[*Location*, window="content"] 파일을 포함합니다.
* 이 ``Location`` 엔티티는 해당 리포지토리 내의 모든 `catalog-info.yaml` 파일을 참조하는 중앙 인덱스 역할을 합니다.
+
``` yaml
apiVersion: backstage.io/v1alpha1
kind: Location
metadata:
  name: all-location-parasol
  description: A collection of Parasol components
spec:
  type: url
  target: ./**/catalog-info.yaml
```
* 플랫폼 엔지니어는 {product_name_rhdh}에 기존의 API, 서비스 및 애플리케이션을 가져오기 위한 소프트웨어 템플릿(Software Templates)을 만듭니다.
* 개발자는 이러한 소프트웨어 템플릿을 사용하여 자신의 컴포넌트를 등록할 수 있습니다. 템플릿은 각 컴포넌트에 대해 `catalog-info.yaml` 파일과 스켈레톤 TechDocs를 자동으로 생성합니다.

{product_name_rhdh}는 Git에서 파일 및 리포지토리 이름을 기반으로 이러한 *Location* 파일을 __자동 검색__ 할 수 있습니다(예: __all-location.yaml__ 파일이 __all-location__으로 시작하는 폴더 내에 있을 경우). 또한 자동 검색 실행 빈도를 정의하는 __스케줄__을 구성할 수 있습니다. 이 워크샵에서는 실행 빈도가 15초로 매우 짧습니다.

하지만 자동 검색을 특정 파일 이름으로 제한하고, API 속도 제한을 초과하지 않도록 스케줄 빈도를 신중하게 설정하는 것이 좋은 관행입니다. GitHub의 속도 제한에 대해 더 알아보려면 https://backstage.io/docs/integrations/github/discovery/[여기^, window="content"]를 클릭하세요.


``` yaml
all-location-entity:
    filters:
        branch: main
    entityFilename: all-location.yaml
    catalogPath: /**/all-location.yaml
    projectPattern: \b(all-location\w*)
    schedule:
        frequency:
            seconds: 15
        initialDelay:
            seconds: 15
        timeout:
            minutes: 3
```

=== 파라솔 애플리케이션 개요

개발자는 기존 Parasol 애플리케이션에 새로운 기능을 빌드하는 작업을 맡게 됩니다. 이 애플리케이션은 다음과 같은 구성 요소들로 이루어져 있습니다.

* `parasol-web` 온라인 웹 앱(Node.js & Angular)
* `parasol-store` 핵심 서비스(Quarkus)
* `parasol-db` 핵심 데이터베이스(PostgreSQL)
* `parasol-api` (OpenAPI 사양)

이 모듈의 다음 섹션에서는 플랫폼 엔지니어와 개발자가 기존 애플리케이션을 온보딩하고, 내·외부 개발 사이클을을 가속화하여 개발자 생산성을 증가시키는 과정을 따라가며 학습할 것입니다.
